# Launch UI polish — before/after evidence

Generated by `scripts/ui-audit.mjs`. Reproduce with:

```bash
node scripts/ui-audit.mjs after light      # against http://localhost:3101
AUDIT_BASE=http://localhost:3100 node scripts/ui-audit.mjs after dark
```

## What is here

| Folder | What it is |
|---|---|
| `before-light/` | 36 shots (9 pages × 375/768/1024/1440) at `7291c17`, **dev server** |
| `after-light/` | 36 shots, **production build** (`next build && next start`) |
| `after-dark/` | 36 shots, production build, dark mode |
| `*.json` | The measurements: axe violations, console errors, header geometry, contrast ratios |

The JSON is the part that matters. Screenshots show you something looks
right; the JSON is what can be diffed and what a later run can be checked
against.

## Three things to know before reading these

**1. The "before" set came from the dev server, the "after" sets from a
production build.** The before pass ran before the mode default was
understood, and the code has since changed, so it cannot be re-shot without
reverting. The differences being demonstrated — a two-row header, "Reach 37 ·
Target 0 · Likely 0" on logged-out `/schools`, "Current plan" on `/pricing`
for a stranger — are none of them dev/prod artefacts. But do not read a
pixel-level diff between a dev and a prod shot as meaningful.

**2. The dark circle at the left edge of every `before-*` shot is Next.js's
own dev indicator** (`<nextjs-portal>`), not a Seeded element. It does not
exist in a production build, which is why it is absent from the `after-*`
sets.

**3. Both light and dark are "the default".** A brand-new visitor gets
`systemSync = true` (`lib/context/design-context.tsx`), so their first paint
follows their OS. A contrast pass in one mode proves nothing about the other
— the first version of the CTA fix measured 2.77:1 in light and 1.79:1 in
dark, and a light-only audit would have shipped it.

## `/family` is captured logged out, deliberately

Local dev points at **staging**, and every staging password was scrambled
after the migration rehearsal, so no account on this machine can sign in.
The `family-*.png` shots are what a visitor hitting the URL sees, not the
signed-in family page. Said plainly rather than quietly omitted.

## Headline numbers (after, production build)

- Header: **73px, 1 row** at 375 / 768 / 1024 / 1280 / 1440 on all 9 pages,
  no horizontal overflow. Before: **94px, wrapped** at 1024 and 1440 on the
  six pages using the shared nav, and **no `<header>` element at all** on
  `/onboarding`.
- **0 axe violations**, light and dark. Before: 1 serious
  (`link-in-text-block`) once the scroll-triggered sections were actually
  rendered.
- **0 console errors.** Vercel Analytics / Speed Insights 404s are filtered:
  those paths are served by Vercel's edge, not by `next start`, so they are
  an artefact of running a production build off-platform. The filter is
  explicit in the script, not silent.
- CTA button vs its band: **14.24:1 light / 14.53:1 dark**. Before: 1.72:1.
- Trust strip: **15px at 6.24:1 light / 7.14:1 dark**. Before: 14px.

## The trap this harness fell into first

The first run reported **0 axe violations** and photographed three blank
bands. `page.screenshot({ fullPage: true })` composites a long page without
ever scrolling it, so every `whileInView` section was still unrendered — the
audit was cleanly measuring a page that did not exist. The script now walks
the page before shooting, and that alone turned 0 violations into 2 real
ones. A clean result from a harness nobody has watched work is not a clean
result.
